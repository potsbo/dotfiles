# Worktree

ファイルを編集する作業は、メインの checkout ではなく git worktree を切ってから始める。調査だけなら不要。

- Claude Code: 組み込みの EnterWorktree を使う。
- Codex: `git worktree add` で新しいブランチの worktree を切り、そこで作業する。

repo 側の CLAUDE.md / AGENTS.md に worktree の指示があるときは、そちらに従う。

# 不在中の自走 (night shift)

ユーザーが終了予定時刻 (`until 15:30`) か長さ (`2h`) を添えて不在を告げたとき
(就寝、会議など) に適用する。Claude Code では `/goal` の条件にこれが書かれる。

目的は、ユーザーが戻ったときに作業が最大限進んでいること。手元の情報で決められる
判断のために止まって返答を待つのは、この目的に反する。過去に何度もそれで止まり、
「自分で考えられないか」と返すだけで良い答えが出てきた。足りないのは情報ではなく
自分で決める許可なので、ここで許可しておく。

## 時間

- 開始時に `date` を打ち、終了予定を絶対時刻で書き出す。各ターンの終わりにも
  `date` を打って残り時間を書く。evaluator は時計を読めず、会話に出た時刻で判断する。
- 持ち時間の最後の 15% (5〜30 分) は検証とレポートに充てる。その時間に入ったら、
  作業の途中でも新しい変更を始めず締めに入る。
- 早く終わったら、依頼の範囲内の検証・テスト追加・見つけた問題の修正に使ってよい。
  範囲外の作業は始めず、レポートに提案として書く。

## 質問の扱い

- ユーザーに質問するツールを使わない。メッセージを質問で終えない。返答を待って止まらない。
- 「後でユーザーに聞けばいい」と仮の答えを積み上げない。迷ったら、まず
  「ユーザーはこれに答えるとき、何かを調べるか、それとも自分の頭の中にしかない
  ことから答えるか」を問う。調べて答えるものなら、同じことを自分で調べて決める。
  コード・履歴・ドキュメントを読み、試せるものは試して確かめる。時間は使ってよい。
  間違いないと言える結論を出し、その結論として進める。決め方の既定:
  - 技術選択: 標準的で保守しやすいもの
  - 実装の詳細・不明な仕様: 既存コードの規約と一般的な慣例に合わせる
  - エラー: 自分で調査して直す。同じ問題で 3 回失敗したら保留にして別の作業に移る
- ユーザーに残してよいのは、どうやってもユーザーにしか答えられないものだけ:
  - ユーザーの意図・好み・優先順位で決まり、repo やドキュメントから読み取れないもの
  - repo の外にある、ユーザーしか知らない事情
  - 実行そのものに人の承認が要るもの: push・merge・deploy、不可逆な削除、
    外部への送信や公開、課金が発生する操作、セキュリティに関わる変更
  これらは「保留」として記録し、独立して進められる作業を続ける。前者 2 つで作業が
  詰まるなら、最も妥当な答えを仮に置いて進め、外れたら戻せるように commit を分ける。
- 保留と仮に置いた答えは、出た時点で `NIGHT_SHIFT.md` (repo 直下、commit しない) に
  追記する。context が要約されても残るようにするため。書式は「質問 / なぜ自分では
  決められないか / 仮に置いた答え / 外れたときの戻し方とコスト」。「なぜ自分では
  決められないか」が書けないなら、それは自分で決めるべきものなので記録せず決める。

## 終わり方

最後のメッセージを次の順のレポートにする。

1. 完了したこと (根拠となるテスト結果やコマンド出力を添える)
2. 自分で決めたことのうち、ユーザーが知っておくべきもの (結論と根拠を短く)
3. ユーザーにしか答えられない質問と、仮に置いた答え。外れたときのコストが高い順に並べる
4. 保留 (実行に承認が要るもの)
5. 残っているリスクと、時間があればやりたかったこと
